# SOLID

SOLID 원칙은 객체지향 프로그래밍에서 소프트웨어 설계의 유연성과 유지보수성을 높이고자 하는 5가지 기본 원칙을 의미함. 이 원칙은 로버트 마틴이 제안한 설계 철학으로, 소프트웨어 설계에서 의존성 문제를 줄이고 재사용성을 극대화하는 데 초점을 맞춤.

***

### 1. S: 단일 책임 원칙(Single Responsibility Principle, SRP)

* 의미 : 클래스는 단 하나의 책임만 가져야 함.
* 목표 : 클래스가 하나의 변경 이유만 가지도록 만들어 유지보수를 쉽게함.
* 예시:
  * 잘못된 설계 : 하나의 클래스가 데이터베이스 처리와 UI 렌더링을 모두 담당
  * 올바른 설계 : 데이터베이스 처리와 UI렌더링을 별도의 클래스로 분리

***

### 2. O: 개방-폐쇄 원칙 (Open/Closed Principle, OCP)

* 의미 : 소프트웨어 엔티티(클래스, 모듈, 함수 등)는 확장에는 열려 있어야 하지만 변경에는 닫혀있어야함.
* 목표 : 기존 코드를 수정하지 않고 새로운 기능을 추가할 수 있도록 설계함.
* 예시 :&#x20;
  * 잘못된 설계 : 새로운 요구사항이 생길 때 기존 클래스의 코드를 변경&#x20;
  * 올바른 설계 : 인터페이스나 추상 클래스를 통해 기능을 확장

***

### 3. L: 리스코프 원칙(Liskov Substitution Princilple, LSP)

* 의미: 자식 클래스는 부모 클래스의 역할을 대체할 수 있어야 함.
* 목표 : 프로그램이 부모 클래스의 인스턴스를 사용하는 경우, 자식 클래스의 인스턴스로 대체해도 동작에 문제가 없어야함.
* 예시 :&#x20;
  * 잘못된 설계 : 자식 클래스가 부모 클랫의 메서드를 무효화하거나 예외를 발생시킴.
  * 올바른 설계  : 자식 클래스가 부모 클래스의 메서드를 올바르게 재정의

***

### 4. I: 인터페이스 분리 원칙(Interface Segregation Priciple, ISP)

* 의미 : 특정 클라이언트가 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 분리해야함.
* 목표 : 필요히지 않은 인터페이스에 대한 의존성을 줄임.
* 예시 :&#x20;
  * 잘못된 설계 : 하나의 인터페이스가 모든 메서드를 포함하여 특정 구현에서 불필요한 메서드까지 강제
  * 올바른 설계 : 역할별로 인터페이스를 분리하여 각 클라이언트가 필요한 메서드만 사용.

***

### 5. D: 의존성 역전 원칙(Dependency Inversion Principle, DIP)

* 의미 : 고수준 모듈이 저수준 모듈에 의존해서는 안되고, 둘 다 추상화된 인터페이스에 의존해야 함.
* 목표 : 구현이 아닌 추상화에 의존함으로써 모듈 간 결합도를 줄임.
* 예시 :&#x20;
  * 잘못된 설계 : 상위 클래스가 하위 클래스의 구체적인 구현에 의존&#x20;
  * 올바른 설계 : 상위 클래스와 하위 클래스 모두 인터페이스나 추상 클래스에 의존

***

### SOLID 원칙의 장점.

1. **유지보수성** : 코드를 수정하더라고 다른 부분에 영향을 최소화
2. **재사용성** : 코드를 다양한 상황에서 쉽게 재사용 가능
3. **확장성** : 새로운 기능 추가가 용이
4. **가독성** : 코드가 명확하고 직관적으로 작성됨.
